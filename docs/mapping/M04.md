# M04 — explicit action checks and supplied omission refutation

Implemented on author-authorized branch `mapping/m00-m05`, based on committed
M03 `3f349fc6b970889346be20775db255ba74c9381a`. Left uncommitted for review.
The governing policy retains M04's M03 dependency, three-day ceiling,
`ergo-sandbox` package, `mapping_actions` target and all three original test names.
Only M04's implementation flag and `completedThrough` advance. M05 is not started.

`map::action::check_actions` consumes explicit, independently named action lists
and independently nominated relation material. Each relation is freshly checked
by M03; a supplied status or discovery edge cannot grant authority. Each action
uses its own canonical spending inputs, data inputs, outputs, input-local extension
material, optional HEIGHT and relation digests. Missing/ambiguous bindings,
unsupported relations, stale derivations and unknown guards remain unresolved.
A false guard leaves that conditional requirement inactive. A different fixed
height needs its own premise bundle and derivation; the API does not infer it.
The normalized guard reads SELF from the concrete spending subject bound to P.

Only a distinct matching spending input satisfies Spend. Data inputs, outputs,
unrelated spending inputs and SELF cannot fill that need. Multiple selectors may
use the same distinct companion; this API adds no cardinality or minimality claim.
Action satisfaction is conditional on the declared premises and does not validate
a transaction, prove necessity, establish simultaneous availability, or say that
the supplied list exhausts protocol actions. Opaque supplied extension material
has no Execute authority in M04. There is no search, request construction, live
source, broadcast, drain integration, detector change, discharge or UI work.

`map::action::refute` takes an explicit versioned witness with claim/premise
digests, a canonical subject input ID and an existing `ValidationRequest`. It
runs the pinned full validator afresh, binds the accepted input to exact SELF,
root and subject, compares every supported state/context component, checks fixed
authentication roots and the normalized true guard, and checks absence of a
distinct matching spending input. A node rejection preserves the validator's
stage and detail; even a script rejection is not universal necessity evidence.
Unknown versions and changed claim/premise digests fail closed. Freshly rebound
digests cannot conceal execution under different premises.

A `Refutation` is not deserializable. Its report retains the claim, witness,
accepted execution and any freshly established static artifact. If both an
accepted omission and establishment exist, status remains `refuted`,
`blocks_release()` is true and the report says `stop-unsound-relation`; the gate
asserts no such conflict. Refutation is not automatically a vulnerability.
The three crate-private helper visibility changes in `check_relation.rs` reuse
its exact selector and guard fragment without changing inference or established
claim data. Existing canonical validation semantics are unchanged.

## Clarification and retained limitation

The [design clarification](../superpowers/specs/2026-09-10-comprehensive-mapping-design.md#m04-implementation-clarification--2026-09-10)
records a correction to an extra test written during this unit: M03 supplemental
control action labels were incorrectly treated as additional M04 gate answers.
Those labels contradict the same fixtures' unsupported claim flags and were not
consumed by M03. All such bytes and prior results remain untouched. The M04 action
answer key remains M00's 67 registered actions; supplemental supported positives
provide extra action checks, and every recorded supplemental accepted omission
still passes fresh refutation. No threshold, corpus row, verdict, denominator,
registered acceptance test or previously established claim was changed.

M05's four positive Execute action expectations and context-code omission family
remain incomplete because that capability belongs to M05. The full 67/67 action
accuracy target remains outstanding there. No M04 stop rule fired; no later unit
was implemented. The supplemental control action-label inconsistency remains
explicitly documented rather than repaired inside this unit.
