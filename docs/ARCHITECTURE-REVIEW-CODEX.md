# Critical architecture review — ergo-forge

Review date: 2026-09-09. This review judges the main worktree's implementation, using the sibling worktrees and measured reports to distinguish historical failures from current limits. References are file-and-line anchors in this checkout; upstream references identify the locally available pinned node revision `9468043396e5daa2828211bcff4234bc70fae4f0`. Measurements below are recorded results, not fresh benchmark runs. Confidential review material informs the architectural conclusions without reproducing its contract findings.

## 1. Is "verify, not trust" architecturally achievable here, or is it marketing?

**Achievable as reproducible verification of explicitly scoped claims; marketing as the present unconditional promise that “a verdict here is the consensus verdict.”** The project has one compiler and one reducer, but several implementations of the context and acceptance conditions surrounding that reducer. A reducer answering correctly about an invented world does not establish that the world can occur, that the transaction validates, or that its outcome violates a protocol's intended policy. These are separate proof obligations, currently collapsed into words such as `valid`, `spendableByAnyone`, and `confirmed`.

The one-engine constraint itself survives inspection. [Cargo.toml:14](../Cargo.toml#L14) pins the node primitives; [compile.rs:85](../ergo-sandbox/src/compile.rs#L85) calls `ergo_compiler::compile`; [eval.rs:347](../ergo-sandbox/src/eval.rs#L347) calls the node reducer. Compose's source generator and independent rule model are not a second ErgoScript compiler or interpreter: they generate a restricted source language and expectations, then submit the source to that compiler ([compose.rs:12](../ergo-sandbox/src/compose.rs#L12)). Neither is a solver that proposes witnesses a forbidden second consensus engine. The constraint should prohibit independent acceptance semantics, not independent hypotheses about what a contract ought to do.

**The architectural break is `txcheck`, not a hidden second interpreter.** [txcheck.rs:206](../ergo-sandbox/src/txcheck.rs#L206) constructs one `Scenario` per input; [txcheck.rs:276](../ergo-sandbox/src/txcheck.rs#L276) implements balance checks itself; [txcheck.rs:313](../ergo-sandbox/src/txcheck.rs#L313) defines validity as an empty problems list. The pinned node already exposes a full validator: [upstream tx/mod.rs:122](/home/rkadias/.cargo/git/checkouts/ergo-99b30a0efa25f868/9468043/ergo-validation/src/tx/mod.rs:122). It performs structural and canonical-wire checks, resolves UTXOs, applies output-height and monetary rules, charges transaction initialization cost, computes the real signing message, verifies scripts/proofs, and applies network re-emission rules. Forge does not call that entry point. This is an architectural omission of validation stages, not a request to patch individual transaction edge cases.

The cost distinction matters even for keyless transactions. `txcheck` gives each scenario a fresh default evaluation budget, whereas the node threads an accumulator through the transaction and charges initialization before scripts ([eval.rs:325](../ergo-sandbox/src/eval.rs#L325); upstream `tx/mod.rs:181`). Additionally, the node's verify wrapper charges deserialize-substitution cost at [upstream reduce.rs:185](/home/rkadias/.cargo/git/checkouts/ergo-99b30a0efa25f868/9468043/ergo-sigma/src/reduce.rs:185). Forge's ordinary unsigned reduction is a preview; its own comment distinguishes that from the optional full verify path ([eval.rs:406](../ergo-sandbox/src/eval.rs#L406)). Calling the same reducer is insufficient to inherit all these acceptance conditions.

Storage rent illustrates why extending `txcheck` check-by-check is the wrong response. Forge has rent explanations, but the node can bypass ordinary script verification through its storage-rent path ([upstream script/mod.rs:147](/home/rkadias/.cargo/git/checkouts/ergo-99b30a0efa25f868/9468043/ergo-validation/src/tx/script/mod.rs:147)). A sidebar about rent does not make the search explore that transition. The same architectural difference can produce false negatives as well as false witnesses.

**The cross-cutting invariant “the oracle is `txcheck::check`, always” should be replaced.** The invariant worth keeping is “only the pinned node's full validation path can establish transaction acceptance.” `txcheck` can remain a useful unsigned preflight and fast candidate filter. Replaying it twice does not independently validate its model. The new confirmation gate currently does exactly that ([audit/triage.rs:100](../ergo-sandbox/src/audit/triage.rs#L100)). Its evidence proves reproducibility under Forge's declared inputs and objective, not mineability.

There is a second, irreducible boundary: consensus does not specify whether a purchase is fair, a reserve release authorized by business policy, or an administrator overprivileged. Those require a separate property specification. “Verify, not trust” can mean “inspect the exact premises, reproduce the accepted transition, and check the stated violation.” It cannot mean “the engine infers what every protocol ought to promise.” Even full local validation remains conditional on the supplied UTXO snapshot and block context; explorer provenance is not independently verified chain membership, and current acceptance is not guaranteed future inclusion.

## 2. Are "playground" and "audit instrument" one product or two?

**One product with two skins.** The common spine is real: authored source and deployed trees can converge on exact ErgoTree bytes; those bytes feed the same evaluator, traces, source anchors, and transaction scenarios. A developer's reproducible failure should become an auditor's candidate witness, and a confirmed protocol defect should become a developer's regression scenario. Splitting products now would duplicate the marshalling and evidence work precisely where duplication already weakens the claim.

The seam should be **synthetic exploration versus evidenced execution**, below both skins. A playground may create money, keys, and a chosen block clock. An audit workspace must distinguish supplied facts, synthetic constructions, observed chain objects, and node-validated transitions. Both may use the same operation; they must not produce indistinguishable result types. A stricter Audit button over the same permissive `ScenarioBox` does not establish that seam.

The present shared spine stops too early. Play and txcheck separately assemble per-input execution and conservation ([play.rs:168](../ergo-sandbox/src/play.rs#L168), [play.rs:209](../ergo-sandbox/src/play.rs#L209); [txcheck.rs:206](../ergo-sandbox/src/txcheck.rs#L206)). Drain builds a third adapter into that stack. That is a reason to unify transaction construction and validation, not evidence that compiler/reducer reuse was a coincidence. Extract a core API around canonical transactions, complete box references, context snapshots, and evidence; let synthetic and chain-backed constructors feed it explicitly.

The web boundary is technically usable: [engine.rs:38](../ergo-web/src/engine.rs#L38) already isolates engine execution behind a shared budget, and routes call the library. The product boundary is incomplete: the router exposes hunt, eval, Play, map, and unsigned validation, but no drain/triage or contextual-audit route ([app.rs:93](../ergo-web/src/app.rs#L93)). Thus the browser's security surface emphasizes the weakest automated detector, while the stronger evidence workflows remain CLI/library operations. Fixing that is eventually necessary; immediately copying every CLI option into the page would expose an expert-only configuration burden without solving it.

Use the playground skin for authoring, explanations, recipe instantiation, and explicit experiments. Use the audit skin for a saved case: exact target, transaction/state provenance, capabilities, property, hypotheses, witnesses, unresolved premises, and replay. Share cases and the execution core. Do not split repositories, invent a second VM, or keep growing four independent meanings of “passes.”

## 3. Where is the architecture actually load-bearing vs. where is it a dead end?

**The core should be the transaction experiment and its evidence, not the decompiler, lint catalogue, or current drain generator.** The most valuable question is whether an independently specified property fails under a reachable, accepted transition. The following ranks the requested subsystems by strategic value per unit of remaining work toward that question, not by implementation size or demo appeal.

## 4. Coverage: what is the tool structurally blind to?

**The roadmap's list is directionally right, but it conflates evaluation support, search expressiveness, observation fidelity, and property expressiveness.** A construct may execute perfectly in a supplied scenario yet be unreachable by the hunt; a found transition may be unscorable; a property may be undefined. More probes address none of those three gaps. The following are boundaries of current abstractions, not assertions that the Ergo reducer cannot execute the contracts.

1. **Protocols whose security objects are not slot-zero singleton-NFT boxes.** Drain rejects an empty `protocolNfts` set and requires each protected input's first token to belong to it ([drain.rs:612](../ergo-sandbox/src/drain.rs#L612)). Ordinary ERG escrows, tokenless vaults, distributed fungible credentials, and otherwise legitimate identities at another token position cannot be represented directly as the victim model. Adding a fictitious NFT changes the target. Identity, value at risk, and attack capabilities need independent fields rather than one protocol-family convention.

2. **Attacks that select a different set of spending inputs.** The search permutes a fixed declared list and changes attacker slots; it does not search membership ([drain.rs:713](../ergo-sandbox/src/drain.rs#L713)). `request_from_map` puts every protected/companion node into one transaction, although a protocol's action boxes are frequently alternatives, and only protected nodes get default successors ([drain.rs:3174](../ergo-sandbox/src/drain.rs#L3174)). An unnecessary co-spend may reject every candidate; a missing companion may conceal an entire route. This is more fundamental than input order, and the roadmap underemphasizes it.

3. **Proof that delegation is unavoidable.** `audit_with_contracts` can reason about a declared same-transaction set; it cannot establish that every spend of A requires B, that a context script's bytes resolve to the authenticated code, or that this code must execute successfully. `Execution::ContextExtension` records a caller assertion ([audit/context.rs:17](../ergo-sandbox/src/audit/context.rs#L17)). Merely making `executeFromVar` printable is not resolving dynamic dispatch. Required co-execution needs an obligation graph with authenticated code resolution and path conditions, not simply more members in `ContractSet`.

4. **Computed and transitive identities in static analysis.** `box_key` can name SELF and positional selectors; computed indices and searched boxes cannot generally become subjects of these findings ([audit/boxrefs.rs:99](../ergo-sandbox/src/audit/boxrefs.rs#L99)). Contextual discharge narrows further to identical literal slots ([audit/context.rs:179](../ergo-sandbox/src/audit/context.rs#L179)). AVL-authenticated credentials, register-derived script identities, data-flow through collection searches, and cross-input equalities cannot be expressed as general authentication chains. The confidential audit confirms that tracing those relationships—not merely printing their operations—is necessary. However, a computed-index contract can still be dynamically evaluated, and a hunt may find a witness if its existing family happens to include one; the early phase-1 specification overstates that particular dynamic exclusion.

5. **The many legitimate ways to authenticate data.** `trust-assumptions` recognizes particular box/token comparisons, explicitly not signatures, AVL proofs, freshness, or transitive authentication ([trust_assumptions.rs:16](../ergo-sandbox/src/audit/lints/trust_assumptions.rs#L16)). Worse, an equality in an irrelevant or negated branch can suppress the local warning. The stricter `required_bindings` reader does not fix that local detector: discharge only visits findings that survived it. This is a semantic-analysis boundary producing both false positives and false negatives, not simply overenthusiastic wording.

6. **General numerical and coupled structural witnesses.** The decoy family scales declared values by fixed factors, changes filler tokens, or clears registers ([drain.rs:2755](../ergo-sandbox/src/drain.rs#L2755)). Fixed-output edits allow one re-tree or prefix padding; first-token replacement and simultaneous edits are explicitly excluded ([drain.rs:820](../ergo-sandbox/src/drain.rs#L820)). Witnesses needing a precise computed reserve, two coordinated output rewrites, or general register updates remain outside the family at any probe cap. Randomness cannot overcome an unchanged generator grammar either.

7. **Oracle selection and manipulation are not one axis.** Current `synthesis.dataInputs` appends a synthetic attacker box with an R4 Long drawn from observed values plus zero ([drain.rs:1575](../ergo-sandbox/src/drain.rs#L1575), [drain.rs:2963](../ergo-sandbox/src/drain.rs#L2963)). It does not generally substitute existing oracle boxes, reorder the data-input set, generate authenticated oracle updates, or change multiple fields. This is useful coverage of “validate one provider, read another,” not completion of roadmap 3c. Creating an arbitrary data box also requires a realizable prior state; the candidate's existence is currently assumed.

8. **Reference-sensitive and historical execution.** The missing box creation reference is information the current `ScenarioBox` cannot store. The txcheck request also lacks the full headers, voted parameters, and transaction context that its chosen height implies. Consequently exact replay of scripts using box bytes, headers, UTXO roots, miner data, historical activation, or rent requires a different execution artifact, not a larger sampling budget. Preserving registers in `ChainBox` was necessary and has landed ([map/source.rs:55](../ergo-sandbox/src/map/source.rs#L55)); missing registers versus an explicitly empty register map still collapse under defaults.

9. **Keyed insiders, partial collusion, and protocol-authorized adversaries.** Victim and companion scripts must reduce to `pass`, regardless of attacker capabilities ([drain.rs:1085](../ergo-sandbox/src/drain.rs#L1085)). An overdraw by a beneficiary, a dishonest authorized updater, or a malicious threshold subset is therefore excluded even when the intended policy restricts those parties. Recognizing P2PK payout scripts is not support for these attackers. The project already has a prover; the missing abstraction is a capability model connected to actual signed transaction witnesses.

10. **Non-extraction security properties and general exchange policies.** The objective recognizes unconditional and declared P2PK receipts, plus bounded static or fixed-rate release terms ([drain.rs:2267](../ergo-sandbox/src/drain.rs#L2267), [drain.rs:328](../ergo-sandbox/src/drain.rs#L328)). Joint payment pools can be refused ([drain.rs:2334](../ergo-sandbox/src/drain.rs#L2334)). Variable-rate AMMs, liquidation fairness, credential corruption, griefing, destruction, permanent loss of progress, and theft parked under an arbitrary subsequently spendable script cannot all be expressed as this extraction predicate. Asset custody diagnostics are not substitutes for those properties. The core needs pluggable, versioned properties, with the current extraction objective one implementation.

11. **Reachability, lifecycle invariants, and liveness.** A supplied malformed SELF says nothing about whether a valid predecessor could create it. A “good” singleton proves uniqueness, not that all bearer credentials remain inside the intended lifecycle. A one-transaction request has no reachable-state set, scheduler, queue evolution, or progress condition. The amendment's claim that one-transaction composition “subsumes” multi-transaction chains is false: conjunction of scripts in one transition and reachability across transitions are distinct problems. Play supplies useful sequence mechanics, but its current sandbox transitions are not a state-space proof.

12. **Discovery outside constant-linked snapshots.** Map extracts 32-byte constants from the lifted representation ([map/refs.rs:145](../ergo-sandbox/src/map/refs.rs#L145)). Constants are useful discovery hints, not the protocol's complete dependency graph: identities can be computed, supplied off chain, stored in state, or authenticated through another structure. `ChainSource` is a lookup interface, not a verified historical-state interface ([map/source.rs:170](../ergo-sandbox/src/map/source.rs#L170)). Reproducible recorded responses establish what the tool saw; they do not establish simultaneous unspentness, chain finality, issuance authenticity, or completeness of the protocol set.

The additional blind spot is **source/deployment equivalence under constant substitution**. The matcher deliberately erases constant types and values into holes and warns that even authorization or branch reachability may differ ([identity.rs:18](../ergo-sandbox/src/identity.rs#L18)). This is useful family identification. A successful structural match cannot transport a source audit onto a deployed tree. Exact bytes or a separately justified equivalence relation are required; placeholder compilation makes this distinction especially consequential.

## 5. The precision problem

**145 findings / 0 real is an architectural precision failure with a few tunable symptoms.** `unchecked-get` answers whether it recognized a local presence guard. The user asks whether an attacker can cause an unauthorized loss or make required progress impossible. The missing implication includes control of the receiver, reachability of the malformed state, required execution, alternative successful paths, and intended behavior. None is obtained by counting more `.get` guards.

The severity model encodes the wrong abstraction. Its documentation classifies anything other than selected context/lambda roots as potentially immovable, explicitly including `OUTPUTS(0)` ([unchecked_get.rs:7](../ergo-sandbox/src/audit/lints/unchecked_get.rs#L7)); `Finding` makes severity mandatory ([finding.rs:38](../ergo-sandbox/src/audit/finding.rs#L38)). An attacker-controlled output with a missing register generally rejects that attempted spend. For a fraud-proof predicate, rejection of malformed evidence may be intended. For immutable SELF state, the question becomes whether an accepted predecessor can create that state and whether another exit exists. These require different obligations even when the local syntax is identical.

Severity should belong to **a violated property in a stated context**, with an explicit impact argument. A local lint may supply an observation category and review priority, but should not default to vulnerability severity. Confidence is a different field: a high-impact suspected violation may remain unconfirmed; a completely reproducible low-impact behavior may be intentional. “Discharged under this transaction premise,” “not reproduced under these bounds,” “accepted transition violating this property,” and “accepted intended behavior” must not share one severity/status ladder.

The confirmation gate makes evidence materially better but chooses too narrow a universal confirmation method. It selects any real local finding and runs an extraction hunt, then correctly says the selected lint need not have caused the extraction ([audit/triage.rs:73](../ergo-sandbox/src/audit/triage.rs#L73), [audit/triage.rs:114](../ergo-sandbox/src/audit/triage.rs#L114)). Nevertheless, `confirmed` lives on that finding. A height-policy observation can acquire confirmation from an unrelated extraction in the same set. Conversely, a genuine lock-up cannot be confirmed by an accepted extraction transaction at all. Confirmation belongs to the claim/witness pair; lint anchors should be supporting or associated evidence with an explicit causal status.

A trustworthy finding needs all of the following, in one preserved artifact:

- **Target identity:** exact trees and constant bindings, source revision/hash where available, exact box bytes/references, snapshot identity, node/compiler revision, and every synthetic or missing field.
- **The violated property:** affected principals/assets, allowed releases or required progress, policy version, and who supplied the policy. “Not NFT-bound” is an observation, not that property.
- **Capabilities and scope:** controlled keys and inputs, assumed resources, permitted setup, fixed external facts, membership choices, search depth, and which declared companions are assumptions versus established obligations.
- **Evidence appropriate to the claim:** a canonical accepted transaction and accounting for extraction; a reachable bad state plus bounded or proven inability to make the required transition for liveness; authenticated code resolution and mandatory execution conditions for delegation.
- **Attribution and limits:** node validation stage/result, execution anchors and traces, comparison with a control or repaired property where meaningful, exact explored family/caps, unsupported semantics, and unresolved obligations. “No witness” must remain distinct from “no violation.”

Suppression is useful only if it records why an obligation is irrelevant or discharged and invalidates when its dependencies change. A reason attached to a source line alone becomes stale when constants, companion code, deployment state, or policy change. Group repeated reads by the underlying obligation—such as witness-schema validity—and retain individual anchors beneath it. Do not replace 143 visible warnings with 143 silent exclusions.

Precision measurement must also distinguish observations from vulnerability claims. A known-benign corpus should include intended throwing predicates, correctly authenticated derived identities, ordinary payments, alternate legitimate spends, and valid state lifecycles. Report false vulnerability claims and unresolved review obligations separately. A raw flag-rate threshold on a mainnet tree corpus measures prevalence, not precision; a public product can pass it and still overwhelm an auditor reviewing one protocol family.

## 6. What should be built next, and in what order?

1. **Introduce an execution-evidence boundary and use the node's full transaction validator for promotion.** Add canonical transaction bytes, complete referenced boxes, explicit block/protocol context, and a capability/signing path. Preserve an explicit synthetic constructor for playground experiments. Keep `txcheck` as preflight; only full validation may create an accepted-transaction artifact, and only property evaluation over that artifact may create a confirmed violation. Replay existing incident and synthetic cases through both paths and classify disagreements by validation stage. **Buys:** the positive half of “verify, not trust”—a portable result whose validity is not decided by Forge's partial transaction model.

2. **Complete A as provenance and deployment binding, while applying the minimal C presentation correction immediately.** Inference has already removed most compilation failures; the next milestone is exact production bindings or exact on-chain trees, with synthetic samples unable to masquerade as either. Carry provenance with artifacts, distinguish unresolved from absent fields, and label structural matches as structural. Fix the v0 assembly limitation in the pinned compiler API and consume the change; do not add a bypass compiler. Meanwhile stop presenting static-only observations as confirmed high-severity vulnerabilities and stop saying “Would validate” for preflight. **Buys:** assurance that the engine answered about the actual target and that the visible claim matches its evidence.

3. **Turn B into transaction-membership and delegation obligations, not automatic global discharge.** Represent action alternatives, required inputs, authenticated extension resolution, and the distinction between observed co-spends and required co-spends. Start with a narrow, independently checked binding vocabulary; use the current required-binding analysis as the first implementation. Feed the same action model into honest transaction construction and adversarial membership changes. **Buys:** the missing link between a single contract and the protocol behavior that makes its local warning meaningful. Acceptance must include a companion-omission counterexample and a two-contract mutant, not just discharge of the original false positives under supplied premises.

4. **Build C around property-specific evidence and measurable auditor effort.** Separate raw observations, obligation discharge, bounded reproduction, and confirmed violations; attach suppression reasons to hashed premises. Let a drain witness confirm an extraction claim, not any selected lint. Add benign and held-out cases, then measure actionable precision and manual obligations per protocol alongside detection. **Buys:** a report someone can use without hand-tracing hundreds of unrelated syntax warnings. A reduction in red labels alone does not satisfy this milestone.

5. **Finish only the demonstrated 3b/3a/3c gaps, against a widened scoreboard.** Preserve the implemented conditional objective and existing output/data-input gains. Add generic first-token replacement to target the remaining bank mutation, membership-aware companion continuations, then typed register and real oracle-selection domains. Include the known two-output counterexample and a held-out register case before claiming coverage. The phase-3 design demanded at least twenty mutants and all five operators; the present five proven mutants do not satisfy that gate. **Buys:** measured growth in expressible attacks, with objective repair distinguished from generator progress. Do not reopen the historical M4 accounting problem as though the current fixed-rate implementation did not exist.

6. **Add explicit attacker capabilities and replayable short lifecycle sequences before a general solver project.** Reuse the wallet prover for owned keys, including authorized-but-malicious principals. Unify saved Play sequences with the case runner, apply full validation at each step, and model provenance of created boxes. Begin with user-supplied setup and depth-two search over a small action set. **Buys:** coverage of insider overdraw, admitted malformed state, and setup-dependent failures that a one-step keyless rearranger structurally excludes. This is useful even if coverage-guided scheduling never improves a benchmark.

7. **Prototype phase 4 as a replaceable numeric proposal engine, then decide whether it earns expansion.** Give it an independent arithmetic mutant and boundary domains; solve only a small supported fragment and replay every candidate through the canonical validation/property path. An incomplete constraint model may propose wrong candidates safely if replay rejects them; it cannot justify an absence-of-bug conclusion. **Buys:** witnesses whose amounts were not hand-fed. Do not promise automatic constraint extraction from the present traces: `ValueLine` stores formatted values, and hot spots aggregate by label rather than a typed symbolic relation ([eval.rs:49](../ergo-sandbox/src/eval.rs#L49), [hot_spots.rs:49](../ergo-sandbox/src/hot_spots.rs#L49)).

8. **Expose the case workflow in the browser, then evaluate scheduling and scale.** Let Read import exact artifacts and display evidence, let Write/Play create and replay cases, and give long searches explicit jobs with cancellation and persistent run records. Defer new recipes and general graph polish. **Buys:** access to the stronger instrument for the nonexpert user promised by the vision, without requiring that user to understand every generator knob.

The roadmap ordering should therefore become **execution fidelity first; A plus immediate C claim correction; B plus contextual C; measured remaining 3b/3a/3c; keyed capabilities and bounded 5; a narrow 4 prototype; evidence-gated 3d; selected 6 only after that evidence exists**. Most A/B/C work is no longer greenfield. The existing amendment correctly deprioritized search depth, but it omitted the acceptance-oracle gap and overstated how much composition alone resolves. The later phase-3 specification is more careful than the umbrella roadmap about objective-first ordering and source fidelity; follow that correction, then update the actual acceptance gates.

**Defer 3d, but do not make chains depend on it.** Search scheduling only matters once the corpus shows valid in-family witnesses missed through budget exhaustion. Conversely, an explicit two-transition case does not need a coverage-guided scheduler to be useful. The roadmap's dependency from chains to successful steering confuses a possible performance optimization with a representational prerequisite.

**Cancel phase 6 as an autonomous vulnerability-discovery commitment on the present architecture.** Retain role proposals, private case storage, and future scheduled replay of already specified cases. Defer unnamed-target sweeps until target provenance, membership, properties, and precision are established; cancel automatic role/policy guesses being promoted into authoritative verdicts. Automation multiplies the current premise burden and false confidence. It does not remove either. The promised disclosure pipeline is a downstream requirement if sweeps are resumed, not the next feature that improves detection.

**Amend the permanent anti-cheat rule rather than contort the solver around it.** A blind generator is valuable as a benchmark baseline, but “the generator never reads the tree” is not a necessary condition for trustworthy discovery. It conflicts with a future solver deriving target path constraints. Reproducibility, no leaked answer-key witnesses, explicit input data, held-out evaluation, and authoritative replay are the important properties. Keep blind and target-guided generators as separately named methods. A target-aware proposal is not a heuristic verdict.

Differential work should compare Forge's assembly and acceptance with the pinned node's **full** transaction pipeline under identical inputs, not call the same reducer twice. Compiler/decompiler round-trip fuzzing remains useful for recovery fidelity; it does not measure vulnerability coverage. A discrepancy first establishes disagreement between two paths, not automatically an upstream consensus defect: the contexts and permitted claims must be equal before assigning blame.

## 7. The one thing

**Make a node-validated execution bundle the only artifact from which the tool can issue a confirmed transaction/property claim.** This is the one-month architectural change I would choose over another lint, another axis, or a general composition engine. It combines the missing type boundary with the missing validator boundary: canonical transaction and box bytes, explicit context and assumptions, full pinned-node validation, and a preserved property/result record. Synthetic scenarios remain useful and visibly synthetic; they cannot be promoted by copying their bytes into an unqualified result.

The month is successful when a user can take one reported positive, inspect every remaining premise, replay its exact transaction through the pinned node pipeline, and check the stated property without trusting Forge's reconstruction. Existing unsigned or synthetic cases that cannot meet that bar should remain preflight results with named gaps. One such end-to-end case is worth more toward this project's promise than another ten thousand successful reductions of contexts the chain could never contain.
